Reload — the first 600 milliseconds

What you see between hitting refresh and the app existing. Today: a cream void with a lone spinner (ProtectedRoute while the Supabase session resolves). Usually that's a <100ms flash — you pay the spinner noise without needing the wait. Occasionally it's seconds (cold connection, paused project) — and then a bare spinner is the weakest possible company.

THE FIELD

What companies do

Slack / Discord: branded splash + rotating quips — earns its keep because their loads are genuinely long; flickers annoyingly when fast. Linear / Notion / YouTube: app shell instantly, skeletons in the content — the modern default; the wait happens inside a familiar room, not a void. Linear's deeper trick: cached-first — last-known data renders immediately, refreshes silently. Everyone's MVP: the lone spinner, which research says makes waits past ~1s feel longer. The pattern worth copying isn't one of these — it's staging: instant shell always, charm only when the wait is real.

Recommendation

  • D. It's B and C composed by timing: the shell answers "where am I" for free on every reload, and Klay only performs when there's genuinely time to watch him — which keeps him scarce (his own rule) and kills the flash-of-splash problem C has.
  • Implementation is one fallback component: ProtectedRoute's loading branch renders the static shell + skeletons immediately, with a 600ms timer gating <PixelKlay animation="grow"/> + a LetterWave verb in the board area. No auth data needed — the chrome is layout, the user block is a skeleton.
  • Future upgrade (separate decision): persist boardStore to localStorage and render last-known boards instead of skeletons — the Linear cached-first feel. Worth its own round; D doesn't block it.

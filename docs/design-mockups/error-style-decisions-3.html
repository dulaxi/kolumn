DECISION 2

Dark mode — toasts are the app's only frozen surface

toast.js hardcodes every color; in dark mode the app re-themes around toasts that stay light. Two fills genuinely break: info (near-white slab, blinding on dark) and the 1px ink border (invisible against a dark page). The saturated fills (lime/copper/honey/red) read fine on both — the same "saturated tones aren't overridden" rule the palette already uses. Implementation is cheap either way: CSS variables work inside react-hot-toast's inline styles, so toast.js just swaps hexes for var(--toast-*) tokens.

Recommendation

  • 1B. The hue split finishes the semantic system the last two branches built: after training users that red means destructive and honey means warning, keeping the delete receipt and the overdue alert dressed as failures is the last contradiction. Bonus: the red delete toast nearly doubles the text contrast of today's copper.
  • 2B. Solid fills are the toast identity — dark mode shouldn't demote them to washes (that's the InlineNotice tier's job). Theme exactly what's broken: the border and the two pale fills. It's ~6 tokens and a mechanical toast.js swap to var() references, which CSS happily resolves inside react-hot-toast's inline styles.
  • Border rule (user-refined): the border's job is separation — saturated fills separate themselves, so they keep the ink border in both themes (a subtle dark rim in dark mode, zero code change); only the two pale fills (info, archive) get the light border, because without it they melt into a dark page.
